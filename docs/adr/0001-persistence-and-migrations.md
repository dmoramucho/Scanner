# ADR-0001 — Database access library and migration tool

- **Status:** accepted
- **Date:** 2026-08-15
- **Stage:** P1 (scaffold). The decision is recorded now; the dependencies land in P2 with
  the first migration, so P1 ships no unused packages.
- **Context refs:** AGENTS.md §3 (data architecture), §4.11 (do not overengineer), §5
  (NOW: versioned migrations, `tenant_id` discipline; LATER: RLS), §6 (stack, dependency
  justification); `docs/architecture/ports.md` §9.

## Context

Every persistence port (`ScopeAuthority`, `ObservationSink`, `AssetRepository`) is backed by
Postgres in M0. The schema is not ORM-shaped: it needs `ON CONFLICT` upserts for idempotent
ingestion, an SP-GiST containment index for `cidr >>= target` scope checks, append-only
evidence tables, and — once §5 moves it to NOW — row-level security policies. Migrations must
follow `expand → migrate → validate → contract`, and the database is never reset to repair one.

Two choices are material enough to record: how adapters talk to Postgres, and how schema
changes are versioned.

## Decision

**Access: psycopg 3, plain SQL, no ORM.** Adapters own their queries. `domain/` never sees
psycopg — the driver appears only under `adapters/`, behind the Protocols in `domain/ports.py`.

**Migrations: Alembic, with revisions written as raw SQL (`op.execute`), not autogenerated
from models.** There is no ORM metadata to autogenerate from, and autogeneration is the exact
mechanism that would quietly drop a partial index or an RLS policy it does not understand.
Alembic is used purely as a versioned, transactional migration runner.

## Alternatives considered

| Option | Why not |
|---|---|
| **SQLAlchemy ORM** (models as the schema of record) | The schema *is* the product here (AGENTS.md §3, §9). Expressing SP-GiST/`ON CONFLICT`/RLS through an ORM means writing raw SQL anyway, plus carrying a mapping layer that invites `domain/` to import it — the §2.1 violation we are most exposed to. |
| **asyncpg** | Faster, but M0 is a batch/collector workload with no async pressure yet, and it drags an async story into every adapter and test. psycopg 3 offers async later if measurement demands it (§4.11: prove the need first). |
| **SQLAlchemy Core (no ORM) for queries** | Query-builder indirection for SQL we would still hand-tune; adds a dependency to the hot path rather than only to the migration path. |
| **Hand-rolled SQL migration runner** (numbered files + a `schema_version` table) | ~150 lines of ordering, locking, transaction, and rollback handling we would own and test forever — reinventing Alembic's core. A dev-time dependency is cheaper than a bespoke one that fails at 03:00. |
| **yoyo-migrations** | Closest to "plain SQL files, small runner", but a much smaller maintainer base and ecosystem than Alembic for the same job. |
| **dbmate / Atlas / sqitch** | Good tools; each adds a non-Python binary to on-prem install, CI, and the runbook for a Python-only project. |

## Trade-off accepted

Alembic pulls **SQLAlchemy** in as a transitive dependency even though we use no ORM. That is
the price: one extra install-time dependency in exchange for a battle-tested version graph,
transactional DDL, and a real downgrade path. The mitigation is a boundary, not a hope —
SQLAlchemy is confined to `migrations/`; `adapters/` and `domain/` import psycopg or nothing.

Writing revisions as raw SQL also means no free autogeneration: every schema change is typed
out. For a schema this security-shaped, explicit is the point.

## Consequences

- P2 adds `psycopg[binary]` (runtime) and `alembic` (migration path) with pinned versions and a
  committed `uv.lock`.
- A CI/lint check should later assert that `sqlalchemy` appears only under `migrations/` — the
  same mechanism as `tests/test_domain_boundary.py`.
- Revisiting is cheap for access (adapters are behind ports), expensive for migrations (the
  version table is durable). If async becomes necessary, psycopg 3's async API is a
  same-library change.

## Still open

Packaging — whether this ships as a module of the OSINT platform or a sibling repo (AGENTS.md
§1) — is *not* decided here. Everything stays deployment- and packaging-agnostic (no build
backend, no install step) until that gets its own ADR. Same for the collector's implementation
language (AGENTS.md §6).
